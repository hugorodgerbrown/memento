How the capture eval works

Memento saves what you tell any AI client about your life. The eval checks whether a client does that the way the policy says: save the right things, skip the rest, and ask when it's someone else's news. It grades what actually lands in the database, not what the model says it did.

Step 1 · The case

A message, and the right reaction to it

The 19 cases live in docs/evals/capture-policy.json. Each is something a real person might type, plus what a good client should store. Dates are written relative to the day the eval runs, so the cases never go stale.

// the "change" case
{
  "message": "Moved into the new flat in
              Porto last weekend!",
  "expect":  "save",
  "entries": [{
    "kind": "memory",
    "happened": "last-weekend/day",
    "supersede_reason": "change"
  }],
  "setup": [{
    "raw_text": "I live in Lisbon", …
  }]
}
  1. message: exactly what the user types.
  2. expect: save, skip, ask first, or either save or ask.
  3. entries: what should be stored: kind, exact words, date and its precision, tags, and whether it replaces an older entry.
  4. happened: resolved on the day. last-weekend means that Saturday or Sunday; /day means day precision, no finer and no coarser.
  5. setup: entries stored before the message arrives. Here, the old fact the new one must replace.
Step 2 · One run

A fresh, sealed room for every attempt

evals/capture.py runs each case the same way. Nothing carries over between runs, and nothing touches real memories.

  1. Start a serverIts own database, memento_eval.
  2. New userA throwaway account with two tokens: one for the model, one for the harness.
  3. SeedThe harness saves the case's setup entries.
  4. Ask Claude CodeThe message, headless. Only Memento connected; none of your settings. Model pinned; skill on or off.
  5. Read backThe harness recalls everything that was stored.
  6. GradeStored entries and the final reply, against the case.

19 cases × 3 runs = 57 graded runs per configuration

Step 3 · Grading

Nine checks; a run passes only if all of them do

Every failure is filed under one of six categories, so a result says what kind of thing went wrong, not just that something did.

The four cases that fail without the skill share a cause. Claude Code loads MCP tool descriptions only when it decides to use a tool, so the capture policy isn't in view when it decides whether to log. A skill's description is always in view.

What the score decides

The bar, and the distiller's version

80%, and never saving what it should have asked about

Sensitive cases differ: someone else’s private news must never be saved without asking, but your own low mood should be kept. A client that clears the bar in its best configuration writes entries directly. One that doesn't still works, but its saves wait in the inbox for the distiller to structure.

The same cases, as inbox notes

make distil-eval sends each message to the inbox and lets the distiller handle it. Nobody is there to ask, so the rules shift:

Save→save the entries, close the note Skip→save nothing, dismiss the note Ask first→save nothing, leave the note open for the user

Three live-only cases are left out: “don't log that”, a client whose calls were refused, and one that isn't told the date. It hasn't run yet: it needs an Anthropic API key.

Read with care

What the numbers can't tell you

  • Three runs per case. 57 out of 57 is strong evidence that the skill fixes the four failing cases, not proof it never fails.
  • Two checks read the reply, not the database. “Did it ask?” and “did it give a receipt?” match wording. Failures are checked by hand; that is how a false “silent save” was caught and corrected.
  • The skill's author could see the cases. A test fails if the skill quotes any eval message, so its examples are new ones that test the same behaviour.
  • One client so far. claude.ai and ChatGPT need OAuth (M8) before they can be measured the same way.
